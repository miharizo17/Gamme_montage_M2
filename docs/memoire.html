Résumé

Ce rapport présente le projet « Génération intelligente de gammes de montage », réalisé dans le cadre du Master MBDS en collaboration avec l'entreprise LOI Confection, spécialisée dans la production textile (chaîne-et-trame, maille et accessoires).

L'objectif était de concevoir et développer une application capable de générer automatiquement une gamme de montage cohérente — la liste ordonnée des opérations nécessaires à l'assemblage d'un vêtement, avec leurs temps standard et les opérateurs compétents — à partir d'une simple description textuelle d'un nouveau prototype, en s'appuyant sur l'historique réel de production de l'entreprise et sur la matrice de compétences des opérateurs par chaîne.

Le travail a couvert l'ensemble du cycle de développement : exploration et nettoyage de plus de 6500 fichiers Excel historiques hétérogènes (« BASE MANING »), conception d'un modèle de données relationnel, construction d'un pipeline d'import robuste, développement d'un moteur de recherche par similarité textuelle (NLP, TF-IDF et similarité cosinus), croisement avec une matrice de compétences reconstruite par chaîne de production, entraînement d'un modèle de Machine Learning (Random Forest) prédisant le temps standard d'une opération lorsqu'aucune donnée historique n'est disponible, puis développement d'une API REST (FastAPI/PostgreSQL) et d'une interface web (React/TypeScript) permettant de générer, corriger, chiffrer en SMV, enregistrer et consulter l'historique des gammes produites.

Les résultats obtenus montrent un pipeline complet et fonctionnel : import de 5989 gammes réelles et de plus de 180 000 lignes d'opérations, un moteur de suggestion d'opérateur tenant compte de la chaîne de production, une recommandation de la chaîne la mieux équipée pour une production donnée, un modèle prédictif entraîné sur 115 800 temps mesurés réels (erreur moyenne de 24,2 secondes, contre 27,2 à 30,3 secondes pour une simple moyenne historique), ainsi qu'une interface permettant à l'agent de méthode de corriger et sauvegarder les gammes générées. La solution constitue un outil d'aide à la décision destiné aux agents de méthode de l'entreprise.

Mots clés : Gamme de montage, NLP, Machine Learning, TF-IDF, FastAPI, React, PostgreSQL, Production textile, SMV.

Abstract

This report presents the project "Intelligent Generation of Garment Assembly Routings", carried out as part of the MBDS Master's program in collaboration with LOI Confection, a textile production company.

The objective was to design and develop an application capable of automatically generating a coherent assembly routing (gamme de montage) — the ordered list of operations required to assemble a garment, with their standard times and competent operators — from a simple free-text description of a new prototype, leveraging the company's real production history and its operator skills matrix per production line.

The work covered the entire development cycle: exploration and cleaning of more than 6500 heterogeneous historical Excel files ("BASE MANING"), design of a relational data model, construction of a robust import pipeline, development of a text-similarity search engine (NLP, TF-IDF and cosine similarity), cross- referencing with a skills matrix rebuilt per production line, training of a Machine Learning model (Random Forest) predicting an operation's standard time when no historical data is available, and development of a REST API (FastAPI/PostgreSQL) and a web interface (React/TypeScript) allowing users to generate, correct, convert to SMV, save and browse the history of produced routings.

The obtained results show a complete and functional pipeline: import of 5989 real routings and over 180,000 operation lines, an operator-suggestion engine that respects production-line boundaries, a recommendation of the best-equipped line for a given production, a predictive model trained on 115,800 real measured times (mean error of 24.2 seconds, versus 27.2-30.3 seconds for a naive historical-average baseline), and an interface allowing the methods engineer to correct and save generated routings. The solution is a decision-support tool intended for the company's methods engineers.

Keywords: Assembly routing, NLP, Machine Learning, TF-IDF, FastAPI, React, PostgreSQL, Textile production, SMV.

Glossaire

Gamme de montage : liste ordonnée des opérations d'assemblage nécessaires à la fabrication d'un vêtement, précisant pour chacune le temps standard, la machine utilisée et l'opérateur affecté.

SMV (Standard Minute Value) : temps total standard, exprimé en minutes, nécessaire pour produire une pièce complète ; il correspond à la somme des temps de toutes les opérations de la gamme.

Chaîne de production : ligne de fabrication physique regroupant un ensemble d'opérateurs dédiés ; deux chaînes différentes n'ont pas les mêmes opérateurs, même si elles portent parfois le même numéro chez des responsables différents.

Matrice de compétences (Skill Matrix) : tableau croisant, pour chaque opérateur, les opérations qu'il a déjà réalisées, avec leur fréquence et leur temps moyen observé.

NLP (Natural Language Processing / Traitement automatique du langage) : ensemble de techniques permettant à un système informatique d'analyser et de comparer des textes.

TF-IDF (Term Frequency – Inverse Document Frequency) : méthode de vectorisation de texte pondérant les mots selon leur fréquence dans un document et leur rareté dans l'ensemble du corpus, utilisée ici pour comparer la description d'un prototype aux gammes historiques.

Similarité cosinus : mesure de similarité entre deux vecteurs (ici, deux textes vectorisés), utilisée pour classer les gammes historiques les plus proches d'une description donnée.

ML (Machine Learning) : sous-domaine de l'intelligence artificielle permettant à un système d'apprendre à partir de données, sans être explicitement programmé pour chaque cas.

ERP (Enterprise Resource Planning) : logiciel de gestion intégré centralisant les activités d'une entreprise ; chez LOI Confection, le module de gamme de montage vient compléter l'ERP existant.

MCD / MLD : Modèle Conceptuel de Données / Modèle Logique de Données, étapes de modélisation d'une base de données relationnelle.

Introduction

Dans l'industrie de la confection textile, la préparation d'une gamme de montage — la définition précise des opérations, de leurs temps standard et des opérateurs affectés — conditionne directement la productivité d'une ligne de production. Une gamme mal calibrée entraîne des goulots d'étranglement, des opérateurs affectés à des tâches qu'ils ne maîtrisent pas, ou une estimation erronée du temps de production (SMV) communiquée au client.

Chez LOI Confection, cette préparation repose aujourd'hui sur l'expertise des agents de méthode, qui s'appuient sur des années de fiches Excel accumulées, dispersées par opérateur, par année et par chaîne de production, sans outil de recherche ni de réutilisation systématique de cet historique. Retrouver la gamme la plus proche d'un nouveau prototype, et identifier quels opérateurs de la chaîne concernée maîtrisent réellement les opérations nécessaires, reste un exercice manuel, lent et dépendant de la mémoire individuelle.

C'est dans ce cadre qu'a été réalisé un stage [à préciser : stage / projet académique] au sein de LOI Confection. Ce choix s'inscrit dans un parcours de formation en Master MBDS et vise à mettre en pratique des compétences en développement, en traitement de données et en intelligence artificielle, tout en répondant à un besoin concret de l'entreprise.

Les missions confiées consistaient notamment à :

  • explorer et fiabiliser l'historique de production disponible (fichiers Excel « BASE MANING »),
  • concevoir une base de données centralisant les gammes, les opérations et les opérateurs,
  • développer un moteur de recherche par similarité textuelle entre une description de prototype et les gammes historiques,
  • croiser ce résultat avec la matrice de compétences des opérateurs, par chaîne de production,
  • exposer une API REST et une interface web permettant de générer, corriger et sauvegarder une gamme.

La problématique de ce travail peut être formulée ainsi :

« Comment automatiser la préparation d'une gamme de montage cohérente à partir de la seule description d'un nouveau prototype, en s'appuyant sur l'historique réel de production et sur les compétences réelles des opérateurs de chaque chaîne ? »

1. Présentation du stage

1.1 Présentation de l'entreprise

Créée en 1995 par Chiheb Bouhali et Chabina Meraly, L.O.I (Lingerie de l'Océan Indien) se spécialise dans la lingerie corsetterie. L'atelier fait partie des pionniers des nouveaux confectionneurs malgaches installés dès le début des années 1990.

En 2001, L.O.I participe en tant que membre fondateur à la création du premier cluster textile de Madagascar : « Text'île Mada », aux côtés de quatre autres usines locales.

En 2009, alors que les ateliers comptent près de 400 collaborateurs, l'entreprise pivote et devient LOI Confection afin de se spécialiser dans un nouveau secteur d'activité : la fabrication de prêt-à-porter en chaîne-et-trame.

Aujourd'hui, LOI Confection compte plus de 800 collaborateurs avec des savoir-faire variés, allant de la confection chaîne-et-trame, à la maille, ainsi qu'à la fabrication d'accessoires textiles. L'entreprise organise sa production en plusieurs chaînes, chacune dotée de son propre effectif d'opérateurs spécialisés, réparties entre plusieurs responsables de méthode.

Le secteur du textile est particulièrement exigeant en termes de qualité, de rapidité et de flexibilité. Dans ce contexte, la préparation des gammes de montage — étape préalable à tout lancement de production — doit être à la fois rapide et fiable, alors qu'elle repose aujourd'hui presque entièrement sur l'expérience individuelle des agents de méthode et sur des fichiers Excel non centralisés.

1.2 Présentation du sujet et objectifs du projet (problème traité)

Le projet porte sur la conception et le développement d'un outil de génération intelligente de gammes de montage, permettant à un agent de méthode de saisir la description libre d'un nouveau prototype et d'obtenir automatiquement une proposition de gamme cohérente : liste ordonnée des opérations, temps standard, machine et opérateur suggéré pour chacune.

Ses objectifs principaux sont les suivants :

  • Centraliser l'historique de production, aujourd'hui dispersé dans plus de 6500 fichiers Excel hétérogènes.
  • Retrouver automatiquement, par similarité textuelle, la gamme historique la plus proche d'une nouvelle description de prototype.
  • Reconstruire une matrice de compétences réelle par chaîne de production, à partir de l'historique des affectations.
  • Suggérer, pour chaque opération, l'opérateur le plus expérimenté sur la chaîne choisie pour la production.
  • Recommander la chaîne la mieux équipée pour réaliser une production donnée, indépendamment de la chaîne historique.
  • Permettre à l'agent de méthode de corriger la proposition (opération, temps, opérateur), de fixer une SMV cible répartie automatiquement sur les opérations, puis de l'enregistrer.
  • Offrir un historique consultable, filtrable par chaîne, avec recherche texte, et toujours modifiable.

Ce projet se distingue par la combinaison d'une approche NLP simple mais robuste (recherche par similarité textuelle) avec une contrainte métier forte et peu triviale : une chaîne de production a ses propres opérateurs, et un opérateur suggéré doit être crédible vis-à-vis de la chaîne réellement choisie pour la production, et non uniquement vis-à-vis de la chaîne qui a historiquement produit un article similaire.

Les principaux enjeux identifiés sont :

  • la réduction du temps de préparation d'une nouvelle gamme,
  • la fiabilisation des affectations d'opérateurs selon leurs compétences réelles,
  • la valorisation d'un historique de production jusqu'ici sous-exploité.

Les principaux risques concernent :

  • la qualité et l'hétérogénéité des données Excel sources (en-têtes variables, lignes parasites, colonnes manquantes),
  • l'incomplétude des temps chronométrés dans une partie non négligeable de l'historique (environ 28 % des gammes réelles),
  • la réutilisation d'un même numéro de chaîne par des responsables différents pour désigner des lignes physiquement distinctes.

2. État de l'art sur le sujet traité

2.1 Critères de comparaison

Les critères retenus pour comparer les approches existantes de génération/réutilisation de gammes sont :

  • Réutilisation de l'historique : capacité à retrouver et exploiter des gammes déjà produites.
  • Prise en compte des compétences : intégration d'une matrice de compétences opérateurs.
  • Capacité de recherche/matching : possibilité de retrouver une gamme proche d'une nouvelle description.
  • Flexibilité : adaptation à des données hétérogènes et incomplètes, fréquentes en PME.
  • Coût et complexité de mise en œuvre.

2.2 Étude de chaque solution au vu des critères

2.2.1 Systèmes PLM/ERP avec module de gammes

Les grands progiciels PLM (Product Lifecycle Management) et certains modules ERP proposent une gestion structurée des gammes, avec des temps standards issus de bases de données de type GSD/MTM (temps prédéterminés). Ces systèmes sont robustes mais coûteux, longs à déployer et peu adaptés à la reprise d'un historique existant hétérogène comme celui de LOI Confection — plusieurs fichiers explorés dans le cadre de ce projet suivaient d'ailleurs un format proche d'un export GSD (codes d'opération standardisés, temps machine), sans toutefois être exploitable directement en base.

2.2.2 Bases de gammes figées / bibliothèques de temps

Une approche plus légère consiste à conserver une bibliothèque de gammes types, sélectionnées manuellement par similitude de modèle. Cette approche reste rapide à mettre en œuvre mais dépend entièrement du jugement humain pour identifier la gamme la plus proche, sans automatisation ni recherche systématique.

2.2.3 Recherche d'information et similarité textuelle (NLP)

Les techniques de recherche d'information, en particulier la vectorisation TF-IDF combinée à une mesure de similarité cosinus, permettent de retrouver automatiquement, au sein d'un corpus de documents, ceux qui sont les plus proches d'une requête textuelle. Cette approche est simple à mettre en œuvre, ne nécessite pas de données d'entraînement supervisées, et s'adapte bien à un corpus évolutif — elle est particulièrement pertinente lorsque, comme ici, chaque gamme historique peut être représentée par un document texte (nom de l'article et libellés des opérations).

2.2.4 Machine Learning appliqué à l'affectation et à la prédiction de temps

Au-delà de la recherche par similarité, des modèles de régression (forêts aléatoires, par exemple) peuvent être entraînés pour prédire un temps d'opération à partir de caractéristiques du prototype. Cette approche est prometteuse mais suppose un historique propre et suffisamment volumineux ; dans ce projet, elle constitue une perspective d'évolution (voir Chapitre 9) plutôt qu'une brique implémentée dès la première version.

3. Étude de l'existant et solution envisagée

3.1 Étude de l'existant

3.1.1 Description externe du système existant (vision utilisateur)

Chez LOI Confection, la préparation d'une gamme de montage repose sur l'expérience des agents de méthode. Pour chaque nouveau prototype, l'agent doit :

  • se remémorer ou rechercher manuellement, parmi des centaines de fichiers Excel, un modèle déjà produit dont il pense qu'il ressemble au nouveau prototype,
  • reprendre à la main la liste des opérations de ce fichier,
  • choisir lui-même les opérateurs, sans outil consolidé de compétences par chaîne,
  • calculer manuellement la SMV totale.

3.1.2 Description interne du système existant (vision développeur/conception)

Sur le plan technique, l'historique de production est stocké sous forme de fichiers Excel individuels, organisés dans une arborescence « Responsable / Année / Chaîne / Fichier.xlsx » (dossier « BASE MANING »). L'exploration menée en début de projet a porté sur 6566 fichiers .xlsx/.xlsm.

Cette exploration a mis en évidence une forte hétérogénéité :

  • la feuille utile n'est pas toujours nommée « EQUILIBRAGE » (variantes : « EQUI », « EQUILIBRÉ À 70 % », noms de modèles...) ; une détection par contenu des en-têtes a été nécessaire en complément de la détection par nom, portant le taux de fichiers exploitables de 5231 à 6122 sur 6566 (94 %),
  • les en-têtes de colonnes varient en casse, en accentuation et en formulation (« Nom op » / « Nom des op », « QTE/H/OPERATION » / « TRGT CHRONO »...),
  • le numéro de poste indiqué dans le fichier (« POSTE N° ») est trop souvent vide ou incohérent pour servir de base à l'ordre des opérations ; l'ordre réel des lignes dans le tableau a donc été retenu comme critère fiable,
  • certains fichiers contiennent, en fin de tableau, un bloc de suivi administratif (chef de chaîne, effectif, minutes produites/présence) qui se confond visuellement avec la liste des opérations,
  • environ 28 % des gammes ne comportent aucun temps chronométré exploitable.

3.2 Critique de l'existant

Points positifs :

  • Un historique de production très riche (plus de 6000 gammes réelles, 188 000 lignes d'opérations après import).
  • Des données suffisamment structurées, une fois nettoyées, pour être exploitées automatiquement.

Points négatifs :

  • Aucune centralisation : chaque fichier est isolé, sans recherche possible.
  • Aucune traçabilité formelle des compétences des opérateurs.
  • Dépendance forte à la mémoire individuelle des agents de méthode.
  • Risque d'erreur lors de la reprise manuelle d'une gamme existante.
  • Aucun calcul automatique de la SMV.

3.3 Solutions envisagées

La solution proposée est une application de génération intelligente de gammes, intégrant :

  • Un pipeline d'import et de nettoyage des fichiers Excel historiques vers une base de données relationnelle unique.
  • Un moteur de matching NLP (TF-IDF + similarité cosinus) retrouvant la gamme historique la plus proche d'une description de prototype.
  • Une matrice de compétences reconstruite à partir de l'historique réel des affectations, par opérateur, par opération et par chaîne.
  • Un modèle de Machine Learning (Random Forest) entraîné sur l'ensemble des temps réellement chronométrés, prédisant un temps standard plausible lorsqu'aucune donnée historique (ni sur la ligne, ni sur l'opérateur) n'est disponible pour une opération.
  • Un moteur de suggestion et de recommandation proposant un opérateur par opération (en priorité sur la chaîne choisie) et une chaîne la mieux équipée pour la production.
  • Un backend FastAPI exposant l'ensemble sous forme d'API REST.
  • Un frontend React/TypeScript permettant de générer, corriger, chiffrer en SMV, enregistrer et consulter l'historique des gammes.

3.4 Objectifs principaux et livrables

Objectifs principaux :

  • Automatiser la proposition d'une gamme de montage à partir d'une description libre.
  • Fiabiliser l'affectation des opérateurs selon leurs compétences réelles et leur chaîne.
  • Offrir un historique centralisé, recherchable et toujours modifiable.

Livrables :

  • Backend FastAPI complet (API REST, moteur de matching, service de génération).
  • Scripts d'import et de nettoyage des données historiques, réutilisables et idempotents.
  • Modèle de Machine Learning entraîné et sauvegardé (script d'entraînement réutilisable, métriques d'évaluation documentées).
  • Base de données PostgreSQL peuplée (schéma documenté).
  • Frontend React fonctionnel (génération, historique, édition).
  • Suite de tests automatisés (pytest, Playwright).
  • Présent rapport.

4. Démarche projet

4.1 Principes de la démarche projet

4.1.1 Activités d'ingénierie logicielle

Le projet a été conduit selon une démarche itérative et incrémentale, chaque fonctionnalité étant spécifiée, développée, testée puis validée avant de passer à la suivante, sur la base de retours réguliers. Cette approche s'est avérée particulièrement adaptée à un contexte où la donnée réelle (les fichiers Excel historiques) réservait des surprises à chaque étape d'exploration, obligeant à ajuster fréquemment la conception initiale.

Les principales activités menées, dans l'ordre où elles se sont enchaînées, sont les suivantes :

  • Exploration des données : analyse statistique des en-têtes de colonnes sur l'ensemble du corpus Excel, avant toute décision de modélisation.
  • Conception du modèle de données : élaboration itérative du schéma relationnel (Article, Gamme, GammeLigne, Opérateur, Compétence), enrichi au fil des besoins (ajout de la notion de chaîne, ajout de la date d'enregistrement).
  • Développement du pipeline d'import : script robuste, idempotent, avec nettoyage progressif (données parasites, extraction de la chaîne).
  • Développement du moteur IA : matching textuel, puis croisement avec la matrice de compétences, puis contrainte de chaîne, puis recommandation de chaîne.
  • Développement de l'API REST puis du frontend, avec vérification systématique en conditions réelles (navigateur piloté) à chaque fonctionnalité livrée.
  • Tests : écriture de tests automatisés au fil de l'eau, à chaque nouvelle fonctionnalité, plutôt qu'en fin de projet.

4.1.2 Méthode de gestion de projet utilisée

Le projet a été conduit selon une méthode agile, en cycles courts : chaque besoin exprimé donnait lieu à une fonctionnalité complète (backend, tests, frontend) livrée et vérifiée avant de passer au besoin suivant. Cette organisation a permis d'absorber les découvertes issues de l'exploration des données réelles (formats hétérogènes, lignes parasites, chevauchement de numérotation de chaînes) sans remettre en cause l'ensemble du planning.

4.1.4 Outils

  • /frontend : application React/TypeScript (pages, composants, client API, types).

4.2 Contraintes et risques sur le projet

4.2.1 Contraintes du projet

  • Fidélité à la donnée source : les corrections apportées aux données importées (suppression de lignes parasites, extraction de la chaîne) devaient rester traçables et ne jamais altérer silencieusement l'information réelle.
  • Une chaîne a ses propres opérateurs : contrainte métier centrale, imposant que toute suggestion d'opérateur soit vérifiée par rapport à la chaîne réellement ciblée par la production, et non uniquement par rapport à l'historique.
  • Réversibilité : les gammes générées ne devaient jamais écraser une gamme historique servant de référence — toute sauvegarde crée un nouvel enregistrement.

7.2.3 Modélisation de données

7.2.3.1 Modèle conceptuel

Le modèle de données central s'articule autour d'un Article (référence produit), lié à une ou plusieurs Gamme (versions successives de la routine d'assemblage), chacune composée de plusieurs GammeLigne ordonnées (une opération). Chaque ligne peut référencer un Opérateur. La Compétence associe un opérateur, une opération et une chaîne, avec un nombre d'occurrences et un temps moyen observé — c'est cette table qui matérialise la matrice de compétences exploitée par le moteur de génération.

7.2.3.2 Modèle logique de données

Article(id, code UNIQUE, nom, description, source, chaine)
Gamme(id, article_id -> Article, date_creation)
GammeLigne(id, gamme_id -> Gamme, ordre, operation_libelle,
           temps_equilibre, target, machine, operateur_id -> Operateur)
Operateur(id, nom, matricule, actif)
Competence(id, operateur_id -> Operateur, operation_libelle, chaine,
           nb_occurrences, temps_moyen,
           UNIQUE(operateur_id, operation_libelle, chaine))

Figure : Modèle logique de données (extrait simplifié — voir Annexe 3 pour le schéma SQL complet).

Deux choix de conception méritent d'être soulignés. D'une part, l'ordre des opérations d'une gamme (ordre) repose exclusivement sur la position réelle des lignes dans le tableau source, le numéro de poste Excel s'étant révélé trop peu fiable. D'autre part, la chaine est une clé composée « responsable::numéro », car un même numéro de chaîne est réutilisé par différents responsables pour désigner des lignes de production physiquement distinctes — une fusion naïve aurait mélangé à tort des équipes d'opérateurs différentes.

7.2.4 Modèle de Machine Learning de prédiction du temps standard

Environ 28 % des gammes historiques ne comportent aucun temps chronométré exploitable, et une opération donnée peut être suggérée à un opérateur qui ne l'a encore jamais réalisée (ni lui, ni personne d'autre sur la chaîne cible n'a de moyenne historique disponible). Pour ces cas, un modèle de régression est entraîné afin de fournir une estimation plausible plutôt que l'absence pure et simple de valeur.

Données d'entraînement : 115 800 lignes réelles (gammes non fictives), dont le temps chronométré est strictement positif — les valeurs nulles ou négatives, résultant d'erreurs de saisie, sont écartées.

Caractéristiques (features) :

  • le libellé de l'opération (texte), vectorisé en TF-IDF (unigrammes et bigrammes, 800 caractéristiques maximum) ;
  • la machine utilisée, encodée en variables indicatrices (one-hot encoding), avec gestion explicite des catégories inconnues en prédiction.

Modèle : forêt aléatoire de régression (RandomForestRegressor, scikit-learn), 200 arbres, profondeur maximale 20, entraînée sur 80 % des données (92 640 lignes) et évaluée sur les 20 % restants (23 160 lignes), jamais vus à l'entraînement.

Tableau 4bis : Évaluation du modèle de prédiction de temps, comparée à des références naïves
ApprocheErreur absolue moyenne (MAE)
Prédiction constante = moyenne globale30,3 s
Prédiction constante = médiane globale27,2 s
Modèle Random Forest (retenu)24,2 s (RMSE 36,6 s, R² = 0,39)

Le gain par rapport aux références naïves est réel mais modeste (R² = 0,39, soit 39 % de la variance expliquée) — cohérent avec la nature des données : des temps saisis à la main sur quatre ans par des dizaines de personnes différentes, sans protocole de chronométrage strictement uniforme. Ce modèle intervient uniquement en dernier niveau de repli, après le temps mesuré et la moyenne historique de l'opérateur, et la valeur qu'il produit est toujours explicitement signalée à l'utilisateur (étiquette « prédit par IA » dans l'interface), jamais présentée comme une mesure fiable.

Le modèle est entraîné hors-ligne (script scripts/entrainer_modele_temps.py) et sauvegardé au format joblib ; il est chargé une seule fois en mémoire par le service d'inférence (service/ml_service.py), qui renvoie None si aucun modèle n'est présent sur le disque — le moteur de génération continue alors de fonctionner normalement, simplement sans ce troisième niveau de repli.

7.2.5 Réalisation du cas d'utilisation « Générer une gamme »

Description du scénario (vision fonctionnelle) :

  1. L'agent de méthode saisit une description et, optionnellement, une chaîne et une SMV cible, puis clique sur « Générer la gamme ».
  2. Le frontend envoie POST /gammes/generer au backend.
  3. Le service de génération interroge le moteur de matching NLP, qui vectorise la description et calcule sa similarité cosinus avec l'ensemble des documents de gammes indexés, et retient la gamme historique la plus proche.
  4. Pour chaque opération de cette gamme, le service interroge la matrice de compétences afin de suggérer l'opérateur le plus expérimenté sur la chaîne cible (avec repli explicite si aucun n'y est trouvé).
  5. Le service calcule également, pour chaque opération sans temps mesuré, une estimation à partir du temps moyen de l'opérateur suggéré.
  6. Le service interroge en parallèle le classement des chaînes les mieux équipées pour l'ensemble des opérations de la gamme.
  7. Si une SMV cible a été fournie, les temps sont redistribués proportionnellement côté frontend.
  8. La réponse JSON (opérations, suggestions, chaîne recommandée) est affichée dans un tableau éditable.

9. Conclusion générale

Le bilan des résultats obtenus pour l'entreprise

Le projet « Génération intelligente de gammes de montage » a permis de concevoir et de déployer une solution logicielle complète, répondant au besoin de LOI Confection de valoriser son historique de production pour accélérer et fiabiliser la préparation des nouvelles gammes.

Résultats principaux obtenus :

  • Centralisation de l'historique de production : 5989 gammes réelles et environ 182 000 lignes d'opérations importées et nettoyées à partir de plus de 6500 fichiers Excel hétérogènes.
  • Moteur de matching NLP (TF-IDF, similarité cosinus) retrouvant automatiquement la gamme historique la plus proche d'une description libre.
  • Matrice de compétences reconstruite automatiquement (≈ 57 700 lignes), respectant la contrainte métier selon laquelle une chaîne a ses propres opérateurs.
  • Recommandation de la chaîne la mieux équipée pour une production donnée, indépendamment de la chaîne historique.
  • Modèle de Machine Learning (Random Forest) entraîné sur 115 800 temps réellement mesurés, utilisé comme dernier niveau de repli pour l'estimation du temps d'une opération inédite (MAE 24,2 s, contre 27,2-30,3 s pour une moyenne naïve).
  • Calcul et répartition automatique de la SMV sur les opérations d'une gamme.
  • Interface web complète de génération, correction, enregistrement et consultation de l'historique, avec édition possible à tout moment.
  • API REST FastAPI documentée automatiquement, et suite de 45 tests automatisés.

Le bilan des problèmes rencontrés et des solutions apportées

Plusieurs difficultés significatives ont été rencontrées au cours du projet :

  • Hétérogénéité extrême des données sources : en-têtes de colonnes variables, feuilles non nommées de façon homogène, numéros de poste peu fiables.
    Solution : détection en deux temps (par nom de feuille puis par contenu), dictionnaire de synonymes construit et validé par échantillonnage progressif, abandon du numéro de poste au profit de l'ordre réel des lignes.
  • Données parasites confondues avec de vraies opérations (bloc de suivi administratif en bas de tableau).
    Solution : analyse de fréquence des libellés d'opération pour isoler les motifs récurrents non liés à une opération de montage, avec une liste volontairement restrictive afin de ne jamais supprimer une opération réelle par excès de zèle.
  • Numérotation de chaîne ambiguë entre responsables : un même numéro de chaîne pouvait désigner deux lignes physiquement distinctes.
    Solution : composition d'une clé de chaîne unique combinant le responsable et le numéro.
  • Temps d'opération manquants sur une part significative de l'historique.
    Solution : repli explicite sur le temps moyen historique de l'opérateur suggéré, toujours signalé comme « estimé » dans l'interface plutôt que présenté comme une valeur mesurée.

Les perspectives du projet

Plusieurs axes d'amélioration et d'évolution sont envisageables :

  • Amélioration du modèle de prédiction de temps (R² actuel de 0,39) par un nettoyage plus poussé des libellés d'opération et des machines (actuellement 1497 valeurs de machine distinctes, en partie des variantes d'écriture d'un même équipement), et par l'ajout de caractéristiques supplémentaires (type de vêtement, chaîne).
  • Introduction d'un balancement de ligne automatique, répartissant la charge de travail entre opérateurs disponibles sur une chaîne.
  • Remplacement ou complément du moteur TF-IDF par des embeddings sémantiques, pour mieux gérer les synonymes et fautes de frappe présents dans les descriptions.
  • Mise en place d'une authentification et d'une gestion des rôles (agent de méthode / responsable).
  • Construction d'un catalogue normalisé d'opérations (aujourd'hui en texte libre), pour fiabiliser davantage les statistiques et le matching.

def _meilleure_competence(db, operation_libelle, chaine):
    """Retourne (competence, meme_chaine) : True si trouve sur la
    bonne chaine, False si repli sur une autre chaine (chaine cible
    connue), None si la chaine cible est inconnue."""
    base_query = (
        db.query(Competence)
        .join(Operateur, Competence.operateur_id == Operateur.id)
        .filter(Competence.operation_libelle == operation_libelle)
        .filter(Operateur.matricule.is_(None))
    )
    if chaine:
        competence = base_query.filter(Competence.chaine == chaine)\
            .order_by(Competence.nb_occurrences.desc()).first()
        if competence is not None:
            return competence, True
        competence = base_query.order_by(Competence.nb_occurrences.desc()).first()
        return competence, (False if competence is not None else None)
    competence = base_query.order_by(Competence.nb_occurrences.desc()).first()
    return competence, None

Annexe 4 : Extraction de la chaîne depuis le chemin source (extrait)

CHAIN_PATTERN = re.compile(r"(CHAINE|CH|LINE|L)\.?\s*0*(\d+)", re.IGNORECASE)

def extraire_chaine(rel_path):
    segments = str(rel_path).split("\\")
    racine = segments[0].strip().upper()
    for segment in segments[1:-1]:
        if re.fullmatch(r"\d{4}", segment.strip()):
            continue  # annee
        m = CHAIN_PATTERN.search(segment)
        if m:
            return f"{racine}::CH{m.group(2).lstrip('0') or '0'}"
    return None
